# mercari-alert-bot

메루카리(mercari.jp) 키워드 알림 봇. 새 매물과 가격 인하를 찾아 텔레그램으로 알립니다.

## 구성

| 파일 | 역할 |
|---|---|
| `check_mercari.py` | 검색·판정(`--mode collect`)과 텔레그램 전송(`--mode send`) |
| `seen_items.json` | 봇의 상태. 이미 본 매물, 보낸 알림, 키워드별 조회 시각 |
| `merge_seen.py` | 실행이 겹쳐 push가 충돌했을 때 상태를 안전하게 병합 |
| `scripts/push_state.sh` | 상태 파일을 원격에 반영(충돌 시 병합 후 재시도) |
| `scripts/squash_history.sh` | git 이력 압축 (아래 "저장소 용량 관리" 참고) |
| `scripts/notify_failure.sh` | 워크플로 실패를 텔레그램으로 알림 |
| `tests/` | 봇 워크플로가 매 실행 전에 돌리는 회귀 테스트 |
| `.github/workflows/mercari-check.yml` | 알림 봇 본체 |
| `.github/workflows/squash-history.yml` | 저장소가 커지면 이력을 자동 압축 |

## 키워드 추가하기

`check_mercari.py`의 `SEARCHES`에 추가하면 됩니다. 새로 추가한 키워드는 **첫 조회에서
기준선만 저장하고 알림을 생략**하므로, 기존 매물이 한꺼번에 알림으로 쏟아지지 않습니다.
다음 조회부터 정상 동작합니다.

**지울 때도 그냥 `SEARCHES`에서 빼면 됩니다.** 다음 실행에서 그 키워드의 조회 기록이
정리됩니다(로그에 `[정리] SEARCHES에 없는 키워드 …`). 정리하지 않으면 나중에 같은
키워드를 되살릴 때 '첫 조회'로 취급되지 않아서, 위의 알림 생략 장치가 동작하지 않고
최대 24시간치 매물이 한꺼번에 쏟아집니다.

## 실행 주기 설정

`check_mercari.py`의 `FULL_SCAN_INTERVAL_SECONDS` 하나로 조절합니다.

| 값 | 동작 | 권장 상황 |
|---|---|---|
| `5 * 60` | 새 매물은 매 실행, 가격 인하는 5분마다 | 1분 주기로 돌릴 때 |
| `0` | 매 실행마다 전부 조회 | 2분 이상 주기로 돌릴 때 |

## 동작 점검

실행 로그에 매번 아래 줄이 남습니다.

```
[점검] 매물 2861개 확인 / 등록시각 있음 2861개 / 판매자ID 모름 387개
```

`등록시각 있음`은 "오래된 매물을 신규로 오인하지 않는" 방어선이 쓰는 값입니다.
이 비율이 절반 아래로 떨어진 채 10분 이상 이어지면 **텔레그램으로 알림이 갑니다** —
로그를 열어 보지 않아도 방어선이 무너진 순간을 알 수 있습니다.

왜 이게 중요하냐면, 등록 시각이 사라져도 봇은 멈추지 않고 **예전 방식(상태 파일만 보고
판단)으로 조용히 되돌아갑니다.** 그러면 오래된 매물 알림이 서서히 늘어나는데,
알려 주지 않으면 원인을 찾기 어렵습니다.

## 고장 감지

이 봇은 평소에 조용한 게 정상이라, 고장이 나도 "새 매물이 없나 보다"와 구분되지 않습니다.
그래서 두 가지 경로로 이상을 알립니다.

| 상황 | 알림 |
|---|---|
| 모든 키워드 검색이 10분 넘게 실패 | `⚠️ 메루카리 알림봇 이상` (이후 6시간마다 최대 1회) |
| 검색이 다시 성공 | `✅ 메루카리 알림봇 정상 복구` |
| **키워드 하나만** 1시간 넘게 실패 | `⚠️ [키워드] 검색이 …분째 실패` |
| 막혔던 키워드가 재개 | `✅ [키워드] 검색 재개` |
| **등록 시각**을 절반 미만만 받아옴 | `⚠️ 메루카리 알림봇 방어선 이상` |
| 등록 시각이 다시 정상 | `✅ 메루카리 알림봇 방어선 복구` |
| **전송이 한 건도 되지 않음** | 실행을 실패로 끝냄 → `⚠️ … 실행 실패` |
| 워크플로 실행 자체가 실패 | `⚠️ … 실행 실패` + 실행 로그 링크 |

키워드 단위 감지가 중요한 이유: 전량 실패는 눈에 띄지만, **키워드 하나만 깨지면
그 키워드 알림만 조용히 멈춥니다.** 다른 키워드가 정상이면 텔레그램은 잠잠하고
로그를 열어 보기 전에는 알 수 없습니다. 판정은 `keyword_checked_at`(등록순 조회가
성공했을 때만 전진하는 값)으로 합니다.

**알림 폭탄을 막는 장치가 핵심입니다.** 봇이 1분마다 돌기 때문에, 실패할 때마다 알리면
하루 1,400건이 넘습니다. 그래서:

- 검색 실패는 한 번으로 알리지 않고 **10분 이상 이어질 때만** 알립니다(일시적 오류 무시).
- 고장이 계속돼도 **6시간당 한 번만** 나갑니다. 간격은 벽시계가 아니라 **고장이 시작된
  시점부터** 셉니다(`outage_bucket`). 벽시계로 세면 구간 경계(UTC 00/06/12/18시)를
  넘는 순간 고장이 이어지는 중인데도 한 건이 더 나갔습니다 — 경계 직전에 시작된
  고장이면 1분 간격으로 두 건이었습니다.
- 키워드 단위 고장도 **1시간 이상** 이어질 때만, 6시간당 한 번 알립니다.
- 봇 전체가 죽은 실행에서는 키워드 알림을 내보내지 않습니다(한 번에 18건이 쏟아지므로).
  **살아난 실행에서도 마찬가지입니다** — 그때는 모든 키워드가 동시에 '오래 막혀 있었다'가
  되어 `✅ [키워드] 검색 재개`가 18건 쏟아지는데, 같은 소식을 `✅ 정상 복구` 한 건이
  이미 전합니다.
- 워크플로 실패는 **성공 → 실패로 바뀐 시점에만** 알립니다. `cancelled`로 끝난 실행은
  건너뜁니다. 1분 주기에서는 실행이 겹칠 때마다 취소가 생기는데(실측 약 9%), 그걸
  '정상 아님'으로 세면 취소 직후의 진짜 실패가 묻혀 버리기 때문입니다.

검증: 24시간 전량 실패 시 알림 5건(10분째 첫 건, 이후 6시간마다),
워크플로 60회 연속 실패 시 알림 1건.

감지할 수 없는 것: **봇이 아예 실행되지 않는 경우**(cron 서비스 중단 등)는 스스로 알 수
없습니다. 워크플로의 5분 스케줄이 백업 역할을 하지만, 완전한 감지는 외부 감시가 필요합니다.

## Actions 탭에서 "취소됨"이 보이는 이유

1분 주기로 돌리는데 한 실행이 50~90초 걸리기 때문에, 실행이 끝나기 전에 다음 트리거가
오면 대기하다가 그다음 트리거에 밀려 취소됩니다(실측 약 9%). **정상 동작입니다.**
`concurrency` 설정이 실행을 하나씩만 돌게 지켜 주는 결과이고, 실측 실행 간격은
평균 0.96분으로 유지됩니다.

## 전송이 막혔을 때

고장 알림은 전부 텔레그램으로 나갑니다. 그러니 **텔레그램 자체가 막히면 알릴 수단도 같이
막힙니다.** 토큰이 바뀌었거나 채팅 ID가 틀렸을 때가 대표적입니다.

그래서 전송 단계는 두 가지로 판단합니다.

| 상황 | 판단 | 처리 |
|---|---|---|
| 다른 알림은 나갔는데 이 건만 실패 | 그 알림 쪽 문제 | 재시도 횟수를 세고 3회에서 포기 |
| 한 건도 나가지 않음 | 전송 경로가 막힘 | 재시도 횟수를 되돌리고 **실행을 실패로 끝냄** |

되돌리는 게 핵심입니다. 예전에는 막힌 실행에서도 재시도 횟수를 올렸고, 대기열이 3건이면
`MAX_CONSECUTIVE_SEND_FAILURES`(5건) 기준에도 걸리지 않아 매 실행 전부 1회씩 올라갔습니다.
1분 주기니까 **텔레그램이 3분만 막혀도 대기열 전체가 조용히 폐기**됐고, 종료 코드는 0이라
Actions 탭은 초록색이었습니다.

실행을 실패로 끝내면 최소한 Actions 탭이 빨간색이 되고, 실패 알림 스크립트가
(`httpx`가 아닌 별도의 `curl` 경로로) 한 번 더 시도합니다.

## 저장소 용량 관리

상태 파일을 매 실행마다 커밋하므로 **git 이력**이 계속 쌓입니다.

- 커밋당 약 1.6KB (git 델타 압축이 잘 먹습니다)
- 1분 주기 기준 **1년에 약 1.2GB**
- 상태 파일 자체는 상한이 있어 **약 2MB에서 멈춥니다** (무한히 커지지 않음)

상한은 `check_mercari.py`와 `merge_seen.py` 양쪽에 적혀 있습니다. 어긋나면 충돌 병합
때마다 상태가 조용히 깎이므로, 두 값이 같은지 테스트가 확인합니다.

즉 정리 대상은 파일이 아니라 이력입니다. `squash-history.yml`이 **매주 저장소 크기를
확인해 임계치(기본 500MB)를 넘을 때만** 이력을 커밋 하나로 압축합니다. 평소에는
크기만 확인하고 아무것도 하지 않습니다.

**`seen_items.json`의 내용을 지우면 안 됩니다.** 이력이 줄지 않을뿐더러(오히려 커밋이
하나 더 늘어납니다), `sent_alerts`를 잃으면 이미 보낸 알림이 다시 나갈 수 있습니다.

압축이 안전한 이유:

1. `git commit-tree`로 **현재 트리를 그대로 가리키는** 부모 없는 커밋을 만듭니다.
   파일을 다시 쓰지 않고 트리 객체를 재사용하므로 상태가 달라질 여지가 없습니다.
2. `--force-with-lease`로 밀어냅니다. 읽은 시점 이후 봇이 상태를 갱신했다면 푸시가
   거부되어 아무것도 잃지 않고, 최신 상태로 다시 시도합니다.
3. 압축이 봇 실행 도중에 떨어져도, 봇은 `push_state.sh`의 병합 경로로 복구합니다.

수동으로 실행하려면 Actions 탭에서 `Squash State History`를 `workflow_dispatch`로
돌리면 됩니다. `dry_run=true`로 크기만 확인할 수도 있습니다.

## 버전 고정

### 파이썬 의존성

`requirements.txt`는 상한을 둡니다(`mercapi~=0.4.2`, `httpx~=0.27`). 이 봇은 1분마다
스스로 배포되는 구조라, 범위를 열어 두면 새 메이저 릴리스가 나온 그 실행부터 검증 없이
운영에 들어갑니다. 올릴 때는 사람이 직접 바꾸고 테스트를 돌립니다.

### 액션 버전

`actions/checkout@v7`, `actions/setup-python@v7`을 씁니다. 둘 다 Node 24에서 네이티브로
동작해서 Node 20 지원 종료 경고가 뜨지 않습니다. 메이저 태그(`@v7`)를 쓰므로 그 안의
패치 업데이트는 자동으로 따라갑니다.

## 한 실행이 오래 붙잡고 있지 않게 하는 장치

`concurrency` 설정 때문에 이 봇은 한 번에 하나만 돕니다. 뒤집어 말하면 **한 실행이
길어지는 동안 봇 전체가 멈춥니다.** 그래서 시간 상한이 두 겹 있습니다.

| 상한 | 값 | 없으면 |
|---|---|---|
| 워크플로 잡 (`timeout-minutes`) | 10분 | GitHub 기본값인 6시간까지 붙잡습니다(예: git push가 네트워크에서 멈출 때) |
| 전송 단계 (`MAX_SEND_SECONDS_PER_RUN`) | 4분 | 텔레그램 레이트리밋은 한 건당 최대 1분을 기다리게 하므로, 건수 상한 40건이 곧 40분이 됩니다 |

상한에 닿으면 남은 대기열은 **그대로 보존한 채** 다음 실행으로 넘깁니다.

## 상태 파일이 깨졌을 때

`seen_items.json`을 읽지 못하면 봇은 **빈 상태로 새로 시작하지 않고 멈춥니다.**
빈 상태로 출발하면 `sent_alerts`를 잃어 이미 보낸 알림이 다시 나가고, 이어지는 저장이
깨진 파일을 정상 파일로 덮어써 되돌릴 원본까지 사라지기 때문입니다. 멈추면 워크플로
실패 알림이 텔레그램으로 가고, 파일은 git에 남아 있으므로 이렇게 복구합니다.

```bash
git checkout HEAD~1 -- seen_items.json
```

push 충돌 병합(`merge_seen.py`)도 같은 기준입니다. 방금 이 실행이 모은 결과를 읽지
못하면 병합을 실패시킵니다 — 원격 상태만 남은 파일을 '병합 결과'라며 push해서 이번
실행의 알림이 소리 없이 사라지는 것보다 낫기 때문입니다.

## 상태 저장은 거짓 성공을 보고하지 않습니다

`scripts/push_state.sh`의 성공/실패는 단순한 종료 코드가 아닙니다. 전송 단계는 알림을
하나 보낼 때마다 이걸 호출하고, **성공 신호를 "전송 기록이 원격에 확정됐다"는 뜻으로 읽어**
다음 알림으로 넘어갑니다. 그래서 push하지 않았는데 성공이라고 하면, 실행이 중간에 끊길 때
이미 보낸 알림이 다음 실행에서 다시 나갑니다.

실제로 그런 경로가 있었습니다. push가 거부된 뒤(1분 주기에서는 실행이 겹쳐 흔히 일어납니다)
원격 상태를 받아오는 `git fetch`가 일시적으로 실패하면, 다음 바퀴에서 커밋은 이미 해 둔
상태라 "변경 없음"으로 보여 `exit 0`으로 끝났습니다.

지금은 "보낼 것이 없다"와 "커밋은 했는데 push를 못 했다"를 구분합니다. 아직 원격에
올라가지 않은 커밋이 남아 있으면 `상태 변경 없음`으로 끝내지 않고, 끝까지 실패하면
실패로 끝냅니다. 워크플로가 저장 단계를 여러 번 부르기 때문에, 앞 호출이 남긴
커밋까지 원격추적 ref와 비교해서 확인합니다.

## 테스트

```bash
python -m unittest discover -s tests
```

`tests/test_check_mercari.py`는 판정·전송 로직을, `tests/test_merge_seen.py`는 충돌 병합을,
`tests/test_push_state.py`는 상태 저장 셸 스크립트를 임시 git 저장소에서 실제로 돌려

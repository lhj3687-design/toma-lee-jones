# mercari-alert-bot

메루카리(mercari.jp) 키워드 알림 봇. 새 매물과 가격 인하를 찾아 텔레그램으로 알립니다.

## 구성

| 파일 | 역할 |
|---|---|
| `check_mercari.py` | 검색·판정(`--mode collect`)과 텔레그램 전송(`--mode send`) |
| `seen_items.json` | 봇의 상태. 이미 본 매물, 보낸 알림, 키워드별 조회 시각 |
| `merge_seen.py` | 실행이 겹쳐 push가 충돌했을 때 상태를 안전하게 병합 |
| `scripts/push_state.sh` | 상태 파일을 원격에 반영(충돌 시 병합 후 재시도) |
| `scripts/squash_history.sh` | git 이력 압축 (아래 "저장소 용량 관리" 참고) |
| `scripts/notify_failure.sh` | 워크플로 실패를 텔레그램으로 알림(막히면 GitHub 이슈로) |
| `scripts/clock_scan.py` | 테스트를 여러 가짜 시각에서 돌려 시계 의존성을 찾음(아래 "테스트" 참고) |
| `tests/` | 봇 워크플로가 매 실행 전에 돌리는 회귀 테스트 |
| `.github/workflows/mercari-check.yml` | 알림 봇 본체 |
| `.github/workflows/squash-history.yml` | 저장소가 커지면 이력을 자동 압축 |
| `.github/workflows/tests.yml` | PR에서 테스트와 시계 스캔을 돌림(아래 "테스트" 참고) |
| `.github/dependabot.yml` | 의존성 새 버전이 나오면 PR을 열어 줌(아래 "버전 고정" 참고) |

## 키워드 추가하기

`check_mercari.py`의 `SEARCHES`에 추가하면 됩니다. 새로 추가한 키워드는 **첫 조회에서
기준선만 저장하고 알림을 생략**하므로, 기존 매물이 한꺼번에 알림으로 쏟아지지 않습니다.
다음 조회부터 정상 동작합니다.

**지울 때도 그냥 `SEARCHES`에서 빼면 됩니다.** 다음 실행에서 그 키워드의 조회 기록이
정리됩니다(로그에 `[정리] SEARCHES에 없는 키워드 …`). 정리하지 않으면 나중에 같은
키워드를 되살릴 때 '첫 조회'로 취급되지 않아서, 위의 알림 생략 장치가 동작하지 않고
최대 24시간치 매물이 한꺼번에 쏟아집니다.

## 실행 주기 설정

**1분 주기는 이 저장소가 만들지 않습니다.** 저장소 밖의 cron 서비스가
`workflow_dispatch`를 1분마다 호출합니다. 워크플로 자체의 `cron`은 5분이고 백업입니다.
실측(연속 297회): dispatch 91% / schedule 9%.

주기를 바꾸려면 **두 곳**을 같이 바꿔야 합니다.

| 상수 | 역할 |
|---|---|
| `FULL_SCAN_INTERVAL_SECONDS` | 가격 인하까지 보는 '전체 조회'를 얼마나 자주 할지 |
| `EXPECTED_RUN_INTERVAL_SECONDS` | 기대 실행 주기. 이보다 느려지면 알립니다(아래 참고) |

| `FULL_SCAN_INTERVAL_SECONDS` | 동작 | 권장 상황 |
|---|---|---|
| `5 * 60` | 새 매물은 매 실행, 가격 인하는 5분마다 | 1분 주기로 돌릴 때 |
| `0` | 매 실행마다 전부 조회 | 2분 이상 주기로 돌릴 때 |

### 그 외부 cron이 죽는 방식

1분 주기를 만드는 것은 cron-job.org의 예약 작업 하나입니다. **저장소 밖에 있으므로
이 저장소의 어떤 테스트도 감시도 그것까지는 보지 못합니다.** 죽는 방식은 세 가지입니다.

| 원인 | 증상 | 성격 |
|---|---|---|
| 토큰(PAT) 만료 | dispatch 호출이 전부 401 | **언젠가 반드시 일어납니다** |
| 연속 실패로 cron-job.org가 작업을 자동 비활성화 | 호출이 아예 멈춤 | 위 문제의 2차 피해 |
| cron-job.org 장애 | 호출이 멈춤 | 드묾 |

봇 쪽에서도 잡히기는 합니다. dispatch가 멈추면 워크플로의 5분 스케줄만 남는데, 그
간격(300초)이 기대 주기의 3배(180초)를 넘으므로 `cadence_alerts`가 10분 뒤 "실행 주기
저하"를 보냅니다. 다만 그 알림은 **"느려졌다"까지만** 말하고 원인은 말하지 않습니다.
새벽에 뭔가 잘못됐을 때 어디를 봐야 하는지가 안 나옵니다.

그래서 cron-job.org 쪽 알림도 켜 둡니다. 구멍을 메우는 게 아니라, **더 빠르고 원인을
바로 말해 주는** 두 번째 신호입니다.

#### 설정 (console.cron-job.org → 작업 → Notify me when…)

| 항목 | |
|---|---|
| execution of the cronjob fails | 켬, **Notify after 3 failures** |
| execution of the cronjob succeeds after it failed before | 켬 |
| the cronjob will be disabled because of too many failures | 켬 — 아래 참고 |
| the server TLS certificate is about to expire | **끔** |
| `Schedule expires` (작업 편집 화면) | **끔** |

**'작업이 비활성화될 때'가 가장 중요합니다.** cron-job.org는 연속 실패가 쌓이면 작업을
스스로 끕니다. 그러면 실패 알림조차 더는 오지 않습니다 — 실패할 일이 없어졌으니까요.
이 알림이 없으면 *작업이 꺼졌다는 사실 자체가* 조용히 지나갑니다.

**`Notify after`를 1이 아니라 3으로 두는 이유**는 이 저장소가 이미 배운 것과 같습니다.
하루 1,440번 실행되므로 일시적 오류 한 번마다 알리면 메일을 무시하게 되고, 그러면 알림
장치가 통째로 무력해집니다(아래 "고장 감지"의 알림 폭탄 방지와 같은 논리). 판단은
비대칭입니다 — 3으로 해서 손해 보는 건 감지가 2분 늦는 것뿐인데, 잡으려는 고장은 전부
저절로 낫지 않는 종류라 2분은 무의미합니다. 그래도 봇 자체 감지(10분)보다 3배 빠릅니다.

TLS 인증서 알림을 끄는 이유는 대상이 `api.github.com`이라 인증서가 알아서 갱신되고,
경고를 봐도 할 수 있는 일이 없기 때문입니다. `Schedule expires`는 켜져 있고 날짜가
지나면 작업이 **조용히** 멈춥니다.

#### 켜 두기만 하지 말고 도착하는지 보세요

URL의 워크플로 이름을 없는 것으로 바꿔(`.../workflows/없는이름.yml/dispatches` → 404)
실패 알림이 실제로 메일함에 오는 것을 확인했습니다(2026-09-13). 확인 중에도 봇은
GitHub 5분 스케줄로 계속 돕니다.

#### 토큰 만료일은 달력에 적어 두세요

위 셋 중 **토큰 만료만 일정이 정해진 고장**입니다. 확률이 아니라 날짜입니다.
github.com/settings/tokens에서 만료일을 확인하고 갱신 일정을 잡아 두세요. 만료되면
그날부터 dispatch가 전부 죽고 봇은 5분 주기로 떨어집니다.

## 동작 점검

실행 로그에 매번 아래 줄이 남습니다.

```
[점검] 매물 2861개 확인 / 등록시각 있음 2861개 / 판매자ID 모름 387개
```

`등록시각 있음`은 "오래된 매물을 신규로 오인하지 않는" 방어선이 쓰는 값입니다.
이 비율이 절반 아래로 떨어진 채 10분 이상 이어지면 **텔레그램으로 알림이 갑니다** —
로그를 열어 보지 않아도 방어선이 무너진 순간을 알 수 있습니다.

왜 이게 중요하냐면, 등록 시각이 사라져도 봇은 멈추지 않고 **예전 방식(상태 파일만 보고
판단)으로 조용히 되돌아갑니다.** 그러면 오래된 매물 알림이 서서히 늘어나는데,
알려 주지 않으면 원인을 찾기 어렵습니다.

## 고장 감지

이 봇은 평소에 조용한 게 정상이라, 고장이 나도 "새 매물이 없나 보다"와 구분되지 않습니다.
그래서 두 가지 경로로 이상을 알립니다.

| 상황 | 알림 |
|---|---|
| 모든 키워드 검색이 10분 넘게 실패 | `⚠️ 메루카리 알림봇 이상` (이후 6시간마다 최대 1회) |
| 검색이 다시 성공 | `✅ 메루카리 알림봇 정상 복구` |
| **키워드 하나만** 1시간 넘게 실패 | `⚠️ [키워드] 검색이 …분째 실패` |
| 막혔던 키워드가 재개 | `✅ [키워드] 검색 재개` |
| **등록 시각**을 절반 미만만 받아옴 | `⚠️ 메루카리 알림봇 방어선 이상` |
| 등록 시각이 다시 정상 | `✅ 메루카리 알림봇 방어선 복구` |
| **전송이 한 건도 되지 않음** | 실행을 실패로 끝냄 → `⚠️ … 실행 실패` |
| 워크플로 실행 자체가 실패 | `⚠️ … 실행 실패` + 실행 로그 링크 |
| **검색은 성공하는데 매물 0건** | `⚠️ 메루카리 알림봇 검색 결과 없음` |
| 매물이 다시 들어옴 | `✅ 메루카리 알림봇 검색 결과 복구` |
| **실행 주기가 느려짐** | `⚠️ 메루카리 알림봇 실행 주기 저하` |
| 주기가 돌아옴 | `✅ 메루카리 알림봇 실행 주기 복구` |
| **텔레그램 자체가 막힘** | GitHub 이슈를 열어 소유자에게 메일 (아래 "전송이 막혔을 때" 참고) |
| **실행이 러너를 못 받고 멈춤** | 감시 워크플로가 끊음 → 되살아난 봇이 `⚠️ … 실행 주기 저하` |
| **실행이 아예 생기지 않음** | 감시 워크플로가 GitHub 이슈 (아래 "봇이 밖에서 멈췄을 때" 참고) |

키워드 단위 감지가 중요한 이유: 전량 실패는 눈에 띄지만, **키워드 하나만 깨지면
그 키워드 알림만 조용히 멈춥니다.** 다른 키워드가 정상이면 텔레그램은 잠잠하고
로그를 열어 보기 전에는 알 수 없습니다. 판정은 `keyword_checked_at`(등록순 조회가
성공했을 때만 전진하는 값)으로 합니다.

**알림 폭탄을 막는 장치가 핵심입니다.** 봇이 1분마다 돌기 때문에, 실패할 때마다 알리면
하루 1,400건이 넘습니다. 그래서:

- 검색 실패는 한 번으로 알리지 않고 **10분 이상 이어질 때만** 알립니다(일시적 오류 무시).
- 고장이 계속돼도 **6시간당 한 번만** 나갑니다. 간격은 벽시계가 아니라 **고장이 시작된
  시점부터** 셉니다(`outage_bucket`). 벽시계로 세면 구간 경계(UTC 00/06/12/18시)를
  넘는 순간 고장이 이어지는 중인데도 한 건이 더 나갔습니다 — 경계 직전에 시작된
  고장이면 1분 간격으로 두 건이었습니다.
- 키워드 단위 고장도 **1시간 이상** 이어질 때만, 6시간당 한 번 알립니다.
- 봇 전체가 죽은 실행에서는 키워드 알림을 내보내지 않습니다(한 번에 18건이 쏟아지므로).
  **살아난 실행에서도 마찬가지입니다** — 그때는 모든 키워드가 동시에 '오래 막혀 있었다'가
  되어 `✅ [키워드] 검색 재개`가 18건 쏟아지는데, 같은 소식을 `✅ 정상 복구` 한 건이
  이미 전합니다.
- 워크플로 실패는 **성공 → 실패로 바뀐 시점에만** 알립니다. `cancelled`로 끝난 실행은
  건너뜁니다. 1분 주기에서는 실행이 겹칠 때마다 취소가 생기는데(실측 약 9%), 그걸
  '정상 아님'으로 세면 취소 직후의 진짜 실패가 묻혀 버리기 때문입니다.

검증: 24시간 전량 실패 시 알림 5건(10분째 첫 건, 이후 6시간마다),
워크플로 60회 연속 실패 시 알림 1건.

### 실행은 성공하는데 제 역할을 못 하는 두 가지

위 감지는 전부 **검색 실패**를 기준으로 합니다. 그래서 "실행도 성공하고 검색도 성공하는데
봇이 제 역할을 못 하는" 상태는 전부 빠져나갔습니다. 두 가지를 따로 잡습니다.

**1) 검색은 성공하는데 매물이 0건**

`search_items`는 예외만 나지 않으면 `succeeded=True`입니다. 메루카리가 200으로 빈 결과를
돌려주면 이렇게 됩니다.

| | 판단 |
|---|---|
| `health_alerts` | `any_success`가 참 → **정상**, `__last_search_ok__`도 전진 |
| `keyword_health_alerts` | `keyword_checked_at`이 전진 → **막힌 키워드 없음** |
| `created_coverage_alerts` | 표본이 없음(`total == 0`) → **판단 보류** |

**모든 신호가 초록인 채로 아무것도 찾지 못합니다.** 카테고리 ID가 바뀌거나 검색 조건이
무효가 되면 실제로 이 모양이 됩니다. 평소 전체 조회가 2,800건씩 나오는 봇에서 18개
키워드가 동시에 0건인 건 정상 변동이 아니므로, 10분 이상 이어지면 알립니다.

**2) 실행 주기가 조용히 느려짐**

1분 주기는 저장소 밖의 cron이 만듭니다(위 "실행 주기 설정" 참고). 그게 멈춰도 봇은
**워크플로의 5분 스케줄로 계속 돕니다.**

| | cron이 멈추면 |
|---|---|
| 봇 | 5분 주기로 계속 돎 |
| 실행 결과 | 전부 성공 |
| 고장 알림 | 하나도 안 울림 |
| 새 매물 알림 | **최대 5분 늦어짐** |

5분 스케줄이 백업이자 동시에 이 저하를 **가려 주는** 셈입니다. 직전 실행과의 간격은
`__last_search_ok__`로 알 수 있으므로(이번 실행이 덮어쓰기 전의 스냅샷을 씁니다),
기대 주기의 3배를 넘는 상태가 10분 이상 이어지면 알립니다. 실행이 겹쳐 취소되는 일이
실측 약 6% 있어서 한두 번 건너뛰는 건 정상으로 봅니다.

> `cadence_alerts`는 `health_alerts`보다 **먼저** 불러야 합니다. `health_alerts`가
> `__last_search_ok__`를 이번 실행 시각으로 덮어쓰기 때문에, 순서가 뒤집히면 간격이
> 0으로 보여 영영 감지하지 못합니다. 테스트가 그 성질을 지킵니다.

감지할 수 없는 것: **봇이 아예 실행되지 않는 경우**(외부 cron과 GitHub 스케줄이 동시에
멈추는 등)는 스스로 알 수 없습니다. 완전한 감지는 외부 감시가 필요합니다.

## Actions 탭에서 "취소됨"이 보이는 이유

1분 주기로 돌리는데 한 실행이 50~90초 걸리기 때문에, 실행이 끝나기 전에 다음 트리거가
오면 대기하다가 그다음 트리거에 밀려 취소됩니다(실측 약 9%). **정상 동작입니다.**
`concurrency` 설정이 실행을 하나씩만 돌게 지켜 주는 결과이고, 실측 실행 간격은
평균 0.96분으로 유지됩니다.

**다만 취소가 몇십 분 넘게 이어지면 그건 정상이 아닙니다.** 정상 취소는 성공한 실행
사이에 드문드문 섞입니다. 성공이 하나도 없이 취소만 줄줄이 이어진다면 앞선 실행
하나가 걸려서 뒤가 전부 밀려나고 있는 것입니다 — 아래 "봇이 밖에서 멈췄을 때"를
보세요.

## 전송이 막혔을 때

고장 알림은 전부 텔레그램으로 나갑니다. 그러니 **텔레그램 자체가 막히면 알릴 수단도 같이
막힙니다.** 토큰이 바뀌었거나 채팅 ID가 틀렸을 때가 대표적입니다.

그래서 전송 단계는 두 가지로 판단합니다.

| 상황 | 판단 | 처리 |
|---|---|---|
| 다른 알림은 나갔는데 이 건만 실패 | 그 알림 쪽 문제 | 재시도 횟수를 세고 3회에서 포기 |
| 한 건도 나가지 않음 | 전송 경로가 막힘 | 재시도 횟수를 되돌리고 **실행을 실패로 끝냄** |

되돌리는 게 핵심입니다. 예전에는 막힌 실행에서도 재시도 횟수를 올렸고, 대기열이 3건이면
`MAX_CONSECUTIVE_SEND_FAILURES`(5건) 기준에도 걸리지 않아 매 실행 전부 1회씩 올라갔습니다.
1분 주기니까 **텔레그램이 3분만 막혀도 대기열 전체가 조용히 폐기**됐고, 종료 코드는 0이라
Actions 탭은 초록색이었습니다.

실행을 실패로 끝내면 최소한 Actions 탭이 빨간색이 되고, 실패 알림 스크립트가
(`httpx`가 아닌 별도의 `curl` 경로로) 한 번 더 시도합니다.

### 그 '한 번 더'가 거짓말을 하고 있었습니다

`notify_failure.sh`는 `curl`의 종료 코드로 전송 성공을 판단했습니다. 그런데 **curl은
`--fail` 없이는 HTTP 401·400에도 종료 코드 0을 돌려줍니다.** 그래서 토큰이 바뀌거나
채팅 ID가 틀린 상황 — 바로 위에서 "대표적"이라고 적은 그 상황 — 에서 아무것도
전송되지 않았는데 로그에는 `실패 알림을 텔레그램으로 보냈습니다`가 남았습니다.

알림 경로가 막혔는지 확인할 **마지막 수단**이 거짓 성공을 보고한 것이라, 로그를 봐도
막힌 줄 알 수 없었습니다. 지금은 HTTP 상태와 텔레그램의 `ok` 필드를 둘 다 확인하고,
실패하면 상태 코드와 응답 본문을 함께 남깁니다. `tests/test_notify_failure.py`가
그 성질을 지킵니다(이 스크립트에는 원래 테스트가 하나도 없었습니다).

### 각 고장이 사람에게 닿는 경로 (전수 대조)

| 고장 | 알림을 만드는 곳 | 전달 경로 | 텔레그램 정상 | 텔레그램 막힘 |
|---|---|---|---|---|
| 전 키워드 10분+ 실패 | `health_alerts` | 대기열 → 전송 단계 | ✅ | ❌ |
| 검색 재성공 | `health_alerts` | 대기열 → 전송 단계 | ✅ | ❌ |
| 키워드 하나 1시간+ 실패 | `keyword_health_alerts` | 대기열 → 전송 단계 | ✅ | ❌ |
| 등록 시각 방어선 | `created_coverage_alerts` | 대기열 → 전송 단계 | ✅ | ❌ |
| 전송이 한 건도 안 됨 | `SendBlocked` | 실행 실패 → `notify_failure.sh` | — | ❌ |
| 워크플로 실행 실패 | 워크플로 | `notify_failure.sh` | ✅ | ❌ |
| 테스트 실패로 조회·전송 건너뜀 | 워크플로 | `notify_failure.sh` | ✅ | ❌ |

**텔레그램이 막히면 위 일곱 가지가 전부 같은 한 구멍으로 빠집니다.**
`notify_failure.sh`도 텔레그램으로 보내기 때문입니다. 게다가 그 마지막 시도는
**딱 한 번**입니다 — 실패 알림은 '성공 → 실패로 바뀐 시점'에만 나가므로(1분 주기에서
매번 알리면 하루 1400건이 되니 필요한 장치입니다), 두 번째 실행부터는 건너뜁니다.

같은 채널로 다시 시도하는 건 의미가 없습니다(막힌 채널로 한 번 더 보내는 것뿐입니다).
일시적인 장애라면 대기열이 보존됐다가 복구될 때 그대로 나가므로 이미 해결돼 있습니다.
그래서 **텔레그램과 독립된 두 번째 경로**를 뒀습니다.

### 텔레그램이 막히면 GitHub 이슈로 알립니다

텔레그램 전송이 실패하면 `notify_failure.sh`가 저장소에 이슈를 엽니다. GitHub이
소유자에게 메일을 보내 주므로, **토큰이 바뀌거나 채팅 ID가 틀려 텔레그램이 통째로
막혀도 사람에게 닿습니다.** 시크릿이 비어 있는 경우도 같습니다 — 예전에는 여기서
조용히 끝냈는데, 그건 '알릴 수단이 아예 없는 상태'를 아무에게도 알리지 않는 것과
같았습니다.

이슈가 쌓이지 않게 하는 장치가 두 겹입니다.

- 이 경로는 **'성공 → 실패로 바뀐 시점'에만** 돕니다. 고장이 이어져도 한 번입니다.
- 같은 제목(`⚠️ 알림 경로가 막혔습니다`)으로 **열려 있는 이슈가 있으면 만들지 않습니다.**
  고장이 반복돼도 하나로 유지되니, 고치신 뒤에 닫아 주세요.

목록을 읽지 못하면 만드는 쪽으로 갑니다(놓치는 것보다 하나 더 나은 쪽). 어차피
전환 시점에만 도는 경로라 한 번을 넘길 수 없습니다. GitHub의 issues 목록에는 PR도
섞여 오므로 걸러 냅니다 — 제목이 비슷한 PR 하나 때문에 이슈가 영영 안 만들어지면
안 되기 때문입니다.

두 워크플로의 `permissions`에 `issues: write`가 필요합니다.

**이 경로가 닿지 않는 곳:** 봇이 **아예 실행되지 않는** 경우입니다(cron 중단 등).
그때는 실패한 실행 자체가 없어서 이 경로도 돌지 않습니다. 그래서 별도 워크플로가
밖에서 봅니다 — 아래 "봇이 밖에서 멈췄을 때"입니다. 다만 그 감시도 같은 GitHub Actions
위에서 돌기 때문에, **Actions 자체가 멈추면 둘 다 조용합니다.** 거기까지 덮으려면
저장소 밖의 감시가 필요합니다.

## 저장소 용량 관리

상태 파일을 매 실행마다 커밋하므로 **git 이력**이 계속 쌓입니다.

| | 값 | 재는 법 |
|---|---|---|
| 증가 속도 | **약 0.8 MB/시간 = 하루 약 19MB = 1년 약 7GB** | 구간이 새로 추가하는 객체만 thin pack으로 묶어 경과 시간으로 나눔 |
| 500MB 도달 | **약 24일** | 저장소 30MB 기준 |
| 커밋 빈도 | 시간당 약 140개 | 한 실행이 `queue` 1건 + 전송 건당 `record` 1건 |
| 상태 파일 | 상한이 있어 **약 4.1MB에서 멈춤** | 아래 항목 단가 × 상한 |

상태 파일 상한은 운영 파일에서 항목 단가를 직접 재서 계산합니다(`seen` 63B, 재출품 지문
175B, `sent_alerts` 26B — 지문이 큰 건 키가 `seller:ID:제목`이라 일본어 제목이 통째로
들어가기 때문입니다). 상한을 곱하면 0.95 + 2.63 + 0.51 = **약 4.1MB**입니다.
예전에 적혀 있던 3.5MB는 지문 상한을 6,000에서 15,000으로 올리기 전 단가로 계산한
값이었습니다.

측정은 **시간당 증가량**으로 합니다. '커밋당 몇 KB'로 재면 안 됩니다 — 같은 기간을 창 크기만
바꿔 재도 값이 크게 달라집니다(실측: 100커밋 창 2.47KB, 200커밋 8.86KB, 429커밋 5.72KB).
git 델타 압축은 어떤 객체들이 한 팩에 함께 들어가느냐에 따라 결과가 달라지기 때문입니다.
반면 시간당 증가량은 창을 바꿔도 0.7~0.8 MB/시간으로 일정했습니다.

### 갱신 순서 고정의 용량 효과는 확인되지 않았습니다

`state_update_order()`로 갱신 순서를 실행과 무관하게 만든 뒤(아래 절 참고), 같은 크기 창
(각 429커밋, 약 3시간)으로 전후를 비교한 결과입니다.

| | 시간당 증가량 |
|---|---|
| 순서 고정 전 (09:34~12:43) | 0.79 MB/시간 |
| 순서 고정 후 (12:54~15:59) | 0.83 MB/시간 |

**차이가 없습니다.** 배포 직후 작은 창으로 재고 −72%, −83%라고 적었던 적이 있는데, 둘 다
측정 방법의 산물이었습니다. 배포 전 시뮬레이션이 −83%를 보인 것도 검사용 조회가 매 실행
순서를 *완전히* 무작위로 섞었기 때문입니다 — 실제 메루카리 결과 순서는 부분적으로만
흔들려서, 애초에 줄일 여지가 그만큼 없었습니다.

그래도 순서 고정은 남겨 둘 이유가 있습니다. 용량이 아니라 **결정성**입니다.

- 같은 매물을 같은 집합으로 다시 보면 저장 결과가 **바이트 단위로 같습니다**(테스트가 확인).
- 갓 올라온 매물이 dict 맨 뒤, 즉 용량 상한에서 **가장 먼** 자리에 놓입니다. 예전에는
  검색 결과 위치에 따라 아무 데나 놓였습니다.

남아 있는 churn의 원인은 특정했습니다. **빠른 조회(등록순만, 약 1,800건)와 전체 조회
(등록순+추천순, 약 2,800건)가 5분마다 교대**하므로 '이번에 관찰한 집합'이 오르내리고,
등록순 조회의 120건 창이 새 매물이 들어올 때마다 밀립니다. 집합이 바뀌는 만큼은 재배치가
일어납니다.

`seen`/`relist_fingerprints`를 키 정렬로 저장하고 최근성을 별도 필드로 옮기면 더 줄 수
있을지 모르지만, 위 경험에 비춰 **먼저 재 보고 판단해야 합니다**(상태 파일 형식 변경 +
`merge_seen.py` 대응 + 마이그레이션이 필요합니다). 한 달에 한 번 압축이면 충분합니다.

### 왜 '갱신 순서'가 용량을 결정하는가

`remember()`는 다시 본 항목을 dict **맨 뒤로** 보냅니다(용량 상한이 앞에서부터 잘라내기
때문에 필요한 처리입니다 — 아래 "상태 파일이…" 절 참고). 그래서 **어떤 순서로 갱신하는지가
곧 상태 파일의 바이트 배치**입니다.

예전에는 검색 결과 순서대로 갱신했습니다. 그런데 메루카리 결과 순서는 매 실행 흔들립니다
(새 매물이 끼어들고 추천순이 바뀝니다). 그러면 **같은 매물을 같은 집합으로 다시 봐도**
1.5MB 한 줄 JSON이 통째로 다시 쓰였습니다. 실제 커밋이 그대로 보여 줍니다.

```
queue Mercari alerts     공통접두 0.00MB  공통접미 0.00MB  변경 1503KB  <- 파일 100%
record alert delivery    공통접두 0.47MB  공통접미 0.93MB  변경  137KB  <- seen은 그대로
```

다만 그 재배치가 **용량에 얼마나 기여했는지는 결국 확인되지 않았습니다**(위 절 참고).
파일이 통째로 다시 쓰이는 것처럼 보여도 git 델타 압축이 상당 부분을 흡수합니다.

지금은 `state_update_order()`로 **매물에 붙어 있는 값**(등록 시각, ID)으로 정렬해 갱신하므로
순서가 실행과 무관합니다. 같은 매물 집합을 봤다면 검색 순서가 어떻든 저장 결과가 같고,
테스트가 그 성질을 직접 확인합니다. 오름차순이라 갓 올라온 매물이 맨 뒤, 즉 용량 상한에서
가장 먼 자리에 놓이는 것도 부수 효과입니다(예전에는 검색 결과 위치에 따라 아무 데나).

정렬 키에 등록 시각을 쓰는 탓에 **테스트 픽스처가 같은 등록 시각을 만들면 순서가 뒤집힙니다.**
한 번 그렇게 봇이 멈췄습니다 — 아래 "테스트" 절 참고.

알림 순서는 예전과 같습니다 — 갱신만 오름차순으로 하고 대기열에 넣을 때 되돌립니다.

상한은 `check_mercari.py`와 `merge_seen.py` 양쪽에 적혀 있습니다. 어긋나면 충돌 병합
때마다 상태가 조용히 깎이므로, 두 값이 같은지 테스트가 확인합니다.

**파일 크기는 증가 속도와 무관합니다.** 커밋당 델타는 파일 크기가 아니라 매 실행
재정렬되는 항목 수가 결정합니다. 같은 조건에서 지문 상한을 6000에서 15000으로 올려
파일이 1.37MB에서 2.63MB가 됐을 때 커밋당 비용은 11.1에서 9.9KB로 오히려 내려갔고
(차이는 측정 노이즈), 늘어난 만큼은 압축 기준 일회성 +0.35MB였습니다. 늘어난 꼬리는
다시 조회되지 않아 git 델타에 거의 기여하지 않기 때문입니다.

즉 정리 대상은 파일이 아니라 이력입니다. `squash-history.yml`이 **매주 저장소 크기를
확인해 임계치(기본 500MB)를 넘을 때만** 이력을 커밋 하나로 압축합니다. 평소에는
크기만 확인하고 아무것도 하지 않습니다. 위 증가 속도면 압축은 **한 달에 한 번 정도**
돌게 됩니다.

**`seen_items.json`의 내용을 지우면 안 됩니다.** 이력이 줄지 않을뿐더러(오히려 커밋이
하나 더 늘어납니다), `sent_alerts`를 잃으면 이미 보낸 알림이 다시 나갈 수 있습니다.

압축이 안전한 이유:

1. `git commit-tree`로 **현재 트리를 그대로 가리키는** 부모 없는 커밋을 만듭니다.
   파일을 다시 쓰지 않고 트리 객체를 재사용하므로 상태가 달라질 여지가 없습니다.
2. `--force-with-lease`로 밀어냅니다. 읽은 시점 이후 봇이 상태를 갱신했다면 푸시가
   거부되어 아무것도 잃지 않고, 최신 상태로 다시 시도합니다.
3. 압축이 봇 실행 도중에 떨어져도, 봇은 `push_state.sh`의 병합 경로로 복구합니다.

수동으로 실행하려면 Actions 탭에서 `Squash State History`를 `workflow_dispatch`로
돌리면 됩니다. `dry_run=true`로 크기만 확인할 수도 있습니다.

**아직 실제로 압축한 적은 없습니다.** 2026-09-12에 `dry_run=true`로 처음 돌려 크기 확인
경로가 동작하는 것만 확인했습니다(`저장소 크기 33 MB / 임계치 500 MB`). 실제 압축 단계는
건너뛰었으므로 **force-push 경로는 여전히 미검증입니다.**

특히 저장소에 브랜치 룰셋을 걸었다면 확인이 필요합니다. 압축은
`git push --force-with-lease`로 부모 없는 커밋을 `main`에 밀어 넣기 때문에,
**`Block force pushes`가 켜져 있으면 영영 실패합니다.** 실패하면 워크플로 실패 알림이
가므로 조용히 묻히지는 않지만, 저장소는 계속 커집니다.

같은 이유로 룰셋의 `Require status checks to pass`도 켜면 안 됩니다 — 봇이 상태 파일을
1분마다 `main`에 직접 push하는데, 그 커밋들에는 체크가 붙을 수 없어 전부 거부됩니다.

## 버전 고정

### 파이썬 의존성

`requirements.txt`는 상한을 둡니다(`mercapi~=0.5.0`, `httpx~=0.28.1`). 이 봇은 1분마다
스스로 배포되는 구조라, 범위를 열어 두면 새 릴리스가 나온 그 실행부터 검증 없이 운영에
들어갑니다. **올릴 때는 반드시 PR로 올려서 CI(`tests.yml`)를 거칩니다** — `main`에 직접
고치면 그 다음 실행이 곧 배포입니다.

**두 줄은 함께 움직입니다.** `mercapi 0.5.0`이 `httpx>=0.28.1,<0.29`를 요구하므로
한쪽만 올릴 수 없습니다. 2026-09-12에 `0.4.2 → 0.5.0`을 올릴 때 실제로 그랬습니다.

#### 언제 올려야 하나

**정기적으로 확인할 필요는 없습니다.** mercapi 릴리스는 4년간 9개, 최근에는 연 1~2회이고
`0.4.2 → 0.5.0` 사이에는 22개월 공백이 있었습니다. 달력에 걸어 두면 헛수고가 대부분입니다.

대신 `.github/dependabot.yml`이 **새 버전이 나오면 PR을 열어 줍니다**(주 1회 확인).
그 PR에 기존 CI가 그대로 돌기 때문에, 초록불이면 머지하시면 됩니다.

그 초록불이 실제로 의미를 가지려면 mercapi 표면을 검사해야 합니다 —
`tests/test_mercapi_surface.py`가 그 역할입니다(아래 "테스트" 참고). 없으면 심볼이
옮겨진 업그레이드도 그대로 통과합니다.

#### 업그레이드할 때 확인한 것 (2026-09-12 기준)

라이브러리가 바뀌면 봇이 기대는 표면이 그대로인지부터 봅니다.

| 확인 | 방법 |
|---|---|
| `mercapi.requests`의 정렬·상태 상수 | `SortBy` / `SortOrder` / `Status` 심볼 존재 확인 |
| `Mercapi.search()` 인자 | `categories` / `sort_by` / `sort_order` / `status` |
| 응답 모델 필드 | `id_` `name` `price` `created` `thumbnails` `item_type` `seller_id` |
| 봇의 httpx 사용 경로 | 로컬 서버를 텔레그램 대역으로 세워 `_telegram_post`를 실제로 태움 |

정렬 상수는 특히 중요합니다. `build_search_options()`가 import 실패 시 **조용히 기본
검색으로 물러나기** 때문에, 이름이 바뀌어도 봇은 죽지 않고 정렬 없이 돕니다(stderr 로그만
남습니다). 즉 업그레이드가 깨져도 눈에 잘 띄지 않으니 미리 확인해야 합니다.

### 액션 버전

`actions/checkout@v7`, `actions/setup-python@v7`을 씁니다. 둘 다 Node 24에서 네이티브로
동작해서 Node 20 지원 종료 경고가 뜨지 않습니다. 메이저 태그(`@v7`)를 쓰므로 그 안의
패치 업데이트는 자동으로 따라갑니다.

## 한 실행이 오래 붙잡고 있지 않게 하는 장치

`concurrency` 설정 때문에 이 봇은 한 번에 하나만 돕니다. 뒤집어 말하면 **한 실행이
길어지는 동안 봇 전체가 멈춥니다.** 그래서 시간 상한이 두 겹 있습니다.

| 상한 | 값 | 없으면 |
|---|---|---|
| 워크플로 잡 (`timeout-minutes`) | 10분 | GitHub 기본값인 6시간까지 붙잡습니다(예: git push가 네트워크에서 멈출 때) |
| 전송 단계 (`MAX_SEND_SECONDS_PER_RUN`) | 4분 | 텔레그램 레이트리밋은 한 건당 최대 1분을 기다리게 하므로, 건수 상한 40건이 곧 40분이 됩니다 |

상한에 닿으면 남은 대기열은 **그대로 보존한 채** 다음 실행으로 넘깁니다.

### 이 상한이 닿지 않는 곳이 있습니다

`timeout-minutes`는 잡이 **시작된 뒤부터** 셉니다. 시작하지 못한 잡에는 영영 걸리지
않습니다. 실제로 그렇게 멈췄습니다 — 아래 절입니다.

## 봇이 밖에서 멈췄을 때

2026-09-12 19:21 UTC, 실행 #6758이 `queued` 상태로 **7시간 18분** 멈췄습니다.
`concurrency` 그룹을 쥔 채였기 때문에 뒤따른 실행 478개가 대기 슬롯에서 밀려나며
전부 취소됐고, 알림이 밤새 끊겼습니다.

무슨 상태였는지가 중요합니다. GitHub API에서 두 상태는 다릅니다.

| | 뜻 | job 레코드 |
|---|---|---|
| `pending` | concurrency 차례를 기다리는 중 | 없음 |
| `queued` | 관문을 통과해 **러너**를 기다리는 중 | 있음 |

#6758은 `queued`였고 job도 만들어져 있었습니다. 즉 concurrency는 이미 통과했고
호스티드 러너 배정만 기다렸는데, GitHub이 러너를 붙이지도 타임아웃으로 끊지도
않았습니다(`updated_at`이 `created_at`과 초 단위까지 동일 — 한 번도 다시 건드린 적이
없다는 뜻입니다).

원인은 저장소 바깥입니다. 공개 저장소라 사용량 한도가 없고, 17분 전 같은 저장소의
Dependabot 실행 4건은 정상으로 러너를 받았으며, githubstatus.com에 그날 인시던트가
없었습니다. **막을 수 없으니 피해 시간을 제한하는 것만 할 수 있습니다.**

### 봇 워크플로 안에서는 고칠 수 없습니다

"첫 스텝에서 오래된 실행을 끊자"가 먼저 떠오르지만 작동하지 않습니다. 그 스텝도 잡이
시작돼야 도는데, 잡이 시작되지 못하는 것 자체가 고장입니다. 자기가 갇힌 문을 안쪽에서
여는 구조입니다. `cancel-in-progress: true`도 답이 아닙니다 — 밀린 대기열을 비우는
따라잡기 실행은 4~5분씩 걸리는데, 1분마다 오는 다음 실행이 그걸 매번 죽이면 대기열이
영영 안 빠집니다.

그래서 **다른 `concurrency` 그룹을 쓰는 별도 워크플로**(`watchdog.yml`)가 10분마다
밖에서 확인합니다.

| 조건 | 하는 일 |
|---|---|
| `queued`로 15분 초과 | 그 실행을 취소 → 대기열이 즉시 풀림 |
| 30분 동안 성공한 실행이 하나도 없음 | GitHub 이슈를 열어 소유자에게 메일 |

취소한 뒤에는 **봇이 스스로 알립니다.** 되살아난 실행이 `cadence_alerts`로 "실행 주기
저하"를 텔레그램에 보냅니다 — 2026-09-13 복구 때 실제로 그렇게 됐습니다
(`health:cadence-slow` 기록). 그래서 감시 워크플로는 텔레그램을 직접 건드리지 않습니다.
이미 검증된 경로에 맡기는 편이 낫습니다.

### `pending`은 절대 건드리지 않습니다

이 도구가 저지를 수 있는 가장 나쁜 실수입니다. 봇이 1분마다 도는 한 `pending`은 **정상
역압**으로 늘 생기므로, 그걸 끊으면 멀쩡한 실행을 계속 죽이게 됩니다 — 고장을 못 잡는
것보다 나쁩니다.

`?status=queued` 필터가 둘을 갈라 줍니다. 실측으로 확인했습니다 — 2026-09-13
03:21~03:34 UTC에 대기 중인 실행을 112회 관측하는 동안, `pending` 실행이 그 필터
결과 배열에 들어온 적은 **0회**입니다. 같은 관측에서 두 가지를 더 알았고 코드가
그대로 반영합니다.

- 정상 실행도 `queued`를 잠깐 지나갑니다(실측 8초 미만). 그래서 시간 임계값이 함께
  필요합니다. 15분은 그 100배가 넘습니다.
- `total_count`가 0보다 큰데 `workflow_runs` 배열은 비어 오는 일이 있습니다(112회 중 5회).
  **개수를 믿으면 안 되고 배열만 봐야 합니다.**

실행이 `queued`와 `pending`을 오가는 것도 관측돼서, 끊기 직전에 상태를 한 번 더 읽고
잡에 러너가 붙지 않았는지 확인한 뒤에만 취소합니다. 잡이 러너를 못 받은 상태는
`runner_id`가 **0이고 `runner_name`이 빈 문자열**입니다(키가 없는 게 아닙니다 —
멈췄던 #6758의 잡을 실제 API로 확인한 값입니다).

### 감시 도구 자신이 깨지면

판정 로직 테스트(`tests/test_watchdog.py`)를 먼저 돌리고, 깨졌으면 아무것도 취소하지
않고 실패로 끝냅니다. 그 실패는 Actions 탭에 빨간불로 남고, GitHub 기본 설정에서는
예약 워크플로가 실패하면 소유자에게 메일이 갑니다.

## 상태 파일이 깨졌을 때

`seen_items.json`을 읽지 못하면 봇은 **빈 상태로 새로 시작하지 않고 멈춥니다.**
빈 상태로 출발하면 `sent_alerts`를 잃어 이미 보낸 알림이 다시 나가고, 이어지는 저장이
깨진 파일을 정상 파일로 덮어써 되돌릴 원본까지 사라지기 때문입니다. 멈추면 워크플로
실패 알림이 텔레그램으로 가고, 파일은 git에 남아 있으므로 이렇게 복구합니다.

```bash
git checkout HEAD~1 -- seen_items.json
```

push 충돌 병합(`merge_seen.py`)도 같은 기준입니다. 방금 이 실행이 모은 결과를 읽지
못하면 병합을 실패시킵니다 — 원격 상태만 남은 파일을 '병합 결과'라며 push해서 이번
실행의 알림이 소리 없이 사라지는 것보다 낫기 때문입니다.

## 상태 저장은 거짓 성공을 보고하지 않습니다

`scripts/push_state.sh`의 성공/실패는 단순한 종료 코드가 아닙니다. 전송 단계는 알림을
하나 보낼 때마다 이걸 호출하고, **성공 신호를 "전송 기록이 원격에 확정됐다"는 뜻으로 읽어**
다음 알림으로 넘어갑니다. 그래서 push하지 않았는데 성공이라고 하면, 실행이 중간에 끊길 때
이미 보낸 알림이 다음 실행에서 다시 나갑니다.

실제로 그런 경로가 있었습니다. push가 거부된 뒤(1분 주기에서는 실행이 겹쳐 흔히 일어납니다)
원격 상태를 받아오는 `git fetch`가 일시적으로 실패하면, 다음 바퀴에서 커밋은 이미 해 둔
상태라 "변경 없음"으로 보여 `exit 0`으로 끝났습니다.

지금은 "보낼 것이 없다"와 "커밋은 했는데 push를 못 했다"를 구분합니다. 아직 원격에
올라가지 않은 커밋이 남아 있으면 `상태 변경 없음`으로 끝내지 않고, 끝까지 실패하면
실패로 끝냅니다. 워크플로가 저장 단계를 여러 번 부르기 때문에, 앞 호출이 남긴
커밋까지 원격추적 ref와 비교해서 확인합니다.

## 병합된 상태는 메모리로 되가져옵니다

push가 거부되면 `push_state.sh`가 원격 상태를 받아 `merge_seen.py`로 병합하고
`seen_items.json`을 그 결과로 고쳐 씁니다. 그런데 **전송 루프는 알림 하나마다 자기
메모리 값으로 파일을 다시 씁니다.** 되읽지 않으면 병합으로 들어온 상대편 기록이 바로
다음 저장에서 사라지고, 그 다음 push는 충돌이 없어 통과하므로 병합 경로가 다시 불려
복구될 기회도 없습니다.

무엇이 사라지느냐가 문제입니다. `sent_alerts`가 사라지면 **상대편이 이미 보낸 알림이
대기열에 되살아나 다시 나갑니다** — 병합 로직이 막으려던 바로 그 일입니다. `seen`이
사라지면 그 매물이 다음 조회에서 신규로 오인되고, 상대편 `pending`이 사라지면 그
알림은 영영 나가지 않습니다.

지금은 push가 성공한 직후 `absorb_pushed_state()`로 파일을 되읽어 메모리에 반영합니다.
대기열만은 순회 중이라 새로 들어온 알림을 뒤에 덧붙이기만 합니다. **병합이 없었다면
파일은 방금 저장한 그대로이므로 이 단계는 아무것도 바꾸지 않습니다** — 평소 실행의
동작은 달라지지 않습니다.

지금 이 결함이 실제로 터지려면 봇 실행 두 개가 겹쳐야 하는데, 워크플로의
`concurrency` 그룹이 실행을 하나씩만 돌게 막고 있습니다. 운영 이력
**1,239개 커밋 구간(압축 전후 main 전체)** 을 훑어 `sent_alerts`·`pending`·
`seen`·`keyword_checked_at`이 설명 없이 줄어든 자리를 찾아봤지만 **0건**이었습니다.

그래도 고쳐 둔 이유는, 이 방어선이 **설정 한 줄**에 걸려 있기 때문입니다. 트리거가
하나 늘거나 다른 워크플로가 상태 파일을 건드리는 순간 겹침이 생기고, 그때 조용히
중복 알림이 나갑니다. `push_state.sh`가 병합 경로를 갖추고 그 경로에 테스트까지
붙여 둔 것 자체가 '겹칠 수 있다'는 전제인데, 그 결과를 한 단계 뒤에서 버리고 있던
셈이었습니다.

**전송되지 않았는데 '보냈습니다'라고 하지 않는지** 확인합니다(위 "전송이 막혔을 때" 참고).
`tests/test_mercapi_surface.py`는 봇이 기대는 mercapi의 표면(정렬 상수, `search()` 인자,
결과 필드)이 그대로인지 확인합니다.
`tests/test_watchdog.py`는 감시 도구가 **멈춘 실행만 끊고 정상 대기 실행은 건드리지
않는지** 확인합니다. 이 고장은 실전에서 재현할 수 없으므로, 판정 함수를 I/O에서 떼어
내고 2026-09-12~13 사고에서 실제로 관측한 응답을 픽스처로 고정했습니다.

이 파일만 **깨끗한 인터프리터를 따로 띄웁니다.** `test_check_mercari.py`가 mercapi를
스텁으로 바꿔치기하기 때문에, 같은 프로세스에서는 진짜 라이브러리를 볼 수 없습니다.
그래서 예전에는 **테스트 전체가 초록이어도 mercapi 호환성은 하나도 검증되지 않았고**,
Dependabot이 mercapi를 올린 PR도 심볼이 옮겨졌든 말든 그대로 초록불이 됐습니다.

### 언제 도는가

| | 무엇을 | 왜 거기서 |
|---|---|---|
| 봇 실행마다 (`mercari-check.yml`) | 유닛 테스트 | 깨진 코드로 알림을 보내지 않기 위해 |
| 10분마다 (`watchdog.yml`) | 감시 도구 테스트만 | 잘못 판단해 멀쩡한 실행을 죽이지 않기 위해 |
| PR마다 (`tests.yml`) | 유닛 테스트 + 시계 스캔 전량 | 머지 **전에** 잡기 위해 |

PR 워크플로는 **`main` push에 걸지 않았습니다.** 봇이 상태 파일을 시간당 약 140번
커밋하므로, push 트리거를 달면 테스트도 시간당 140번 돌면서 러너를 잡아먹고 봇 실행과
자리를 다툽니다. `main`의 검증은 봇이 매 실행 전에 돌리는 같은 테스트가 맡습니다.

시계 스캔을 PR에만 둔 이유도 같습니다 — 몇 분이 걸려서 1분 주기 실행 경로에는 들어갈 수
없습니다. 상시 방어선은 매 실행 도는 유닛 테스트 안의
`test_outage_alert_ids_never_depend_on_the_wall_clock`이 맡습니다(아래 참고).

봇 워크플로가 매 실행 전에 이 테스트를 돌리므로, 실패하면 그 실행은 알림을 보내지 않습니다.
**그래서 테스트가 시계에 의존하면 곧바로 봇 장애가 됩니다.** 두 번 겪었습니다.

**1) 벽시계 구간 (2026-09-12 05:49)** — 고장 알림의 `alert_id`가 벽시계 구간에 묶여 있던
탓에 경계 앞 10분 동안만 세 테스트가 깨졌고, UTC 05:49~05:59에 11회 연속 실패로 봇이
멈췄습니다(하루 네 번 반복될 수 있던 문제). 지금은 쿨다운 구간을 고장 시작 시점 기준으로
세고, 해당 테스트들은 일부러 벽시계 경계를 걸치는 시각으로 그 성질을 지킵니다.

**2) 시계 해상도 (2026-09-12 13:18)** — 상태 갱신 순서를 (등록 시각, ID)로 고정한 뒤,
픽스처의 기본 등록 시각이 `datetime.now()`라 **연속 생성된 두 매물이 같은 값을 받는 일**이
생겼습니다(실측 약 1.7%). 그러면 ID가 동점을 가르면서 '나중에 만든 게 더 최근'이라는
전제가 깨져 순서를 단정하는 테스트 두 개가 뒤집혔습니다. run #6358이 그렇게 실패해
그 실행의 조회·전송이 건너뛰어졌습니다. 1분 주기에서 1.7%는 하루 스무 번 넘는 장애입니다.

지금은 픽스처가 생성 순서대로 1마이크로초씩 벌린 등록 시각을 주고(`distinct_created`),
순서를 단정하는 테스트는 등록 시각을 **명시**합니다. 그 성질 자체도 테스트가 지킵니다
(`test_fixture_listings_never_share_a_created_time`).

교훈이 같습니다 — **테스트가 시계에서 읽은 값을 기대값의 근거로 쓰면 안 됩니다.**
기대 순서가 '어느 쪽이 더 최근인지'에 달려 있다면 픽스처가 그걸 명시해야 합니다.

### 시계 의존성은 이제 전수로 확인합니다

위 두 건은 **고친 그 자리만** 막혀 있었습니다. 새로 추가되는 코드는 자동으로
보호받지 못하고, 평소 CI는 '지금 이 순간' 한 시각에서만 돌기 때문에 하루 중 특정
10분에만 어긋나는 결합은 그대로 통과합니다. 그래서 두 겹을 뒀습니다.

**1) 매 실행 — `test_outage_alert_ids_never_depend_on_the_wall_clock`**

쿨다운을 거는 고장 알림 전부(전량 실패 / 등록 시각 방어선 / 키워드 단위)에 대해,
고장이 **하루 중 어느 시각에 시작되든** 24시간 동안 나가는 `alert_id` 목록이 같은지
확인합니다. 68개 시각(30분 간격 + 쿨다운 경계 앞뒤 1초 + 첫 알림이 경계를 걸치는 자리)을
훑는데 0.1초면 끝나므로 매분 실행 경로에 그대로 들어가 있습니다.

새 고장 알림을 추가하면 `OUTAGE_ALERT_FAMILIES`에 한 줄 더해 주세요. 그 한 줄이
그 알림을 같은 방어선 안에 넣습니다.

**2) PR마다 — `scripts/clock_scan.py`**

`tests/test_check_mercari.py` **전체**를 여러 가짜 시각에서 돌립니다(나머지 두 테스트
파일은 시각을 쓰지 않습니다). `tests.yml`이 PR마다 `--day`와
`--repeat 100`을 돌리고, 시각을 다루는 코드를 건드렸을 때 직접 돌려 볼 수도 있습니다.

```bash
python scripts/clock_scan.py --day        # 하루를 5분 간격으로 (288개 시각)
python scripts/clock_scan.py --week       # 7일을 31분 간격으로 (325개 시각)
python scripts/clock_scan.py --repeat 200 # 시계를 그대로 두고 200회 (경합 탐지)
```

몇 분 걸리므로 봇의 매분 실행 경로에는 넣지 않았습니다. PR이 그 자리입니다.

**두 모드는 서로를 대체하지 못합니다.** `--day`/`--week`는 `datetime.now()`를 계산이
한 겹 더 붙은 함수로 바꿔 끼우는데, 그 계산이 연속 호출 사이에 시간을 벌어 주는 탓에
**위 2)번 같은 시계 해상도 경합은 이 모드에서 재현되지 않습니다**(실측: 사고 2)를
되살려 놓고 `--day` 경로로 3회 돌렸을 때 0건 검출, `--repeat`으로는 10회 중 10회 검출).
둘 다 돌려 주세요.

**현재 감사 결과 (2026-09-12).** 위 도구로 하루 288개 시각 + 7일 325개 시각 + 같은
시각 250회, 총 863회를 돌려 전부 통과했습니다. 코드 쪽도 함께 훑었습니다.

| 확인한 것 | 결과 |
|---|---|
| 프로덕션의 시각 소스 | `current_time()` 한 곳뿐 (테스트에서 갈아끼울 수 있게 분리돼 있음) |
| 벽시계 절대값을 구간으로 나누는 코드 | **없음** — 세 곳의 `bucket` 전부 `outage_bucket(경과시간)` |
| `alert_id` 7종 | 전부 이벤트 자체 시각 + 상대 구간. 벽시계 구간 없음 |
| 타임존 | `mercapi`가 `fromtimestamp()`(naive 지역시)로 만든 값을 `.timestamp()`로 되돌리므로 상쇄됨. DST 되돌림 구간까지 왕복 오차 0 |
| 셸 스크립트·워크플로 | `date` 사용 없음 |

검증 방법: 두 사고의 코드를 일부러 되살려 놓고 도구가 잡는지 확인했습니다
(사고 1) 288/288 시각에서 검출, 사고 2) `--repeat` 10/10 검출). 잡지 못하는 도구로
"이상 없음"을 말하지 않기 위해서입니다.

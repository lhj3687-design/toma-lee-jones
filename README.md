# mercari-alert-bot

메루카리(mercari.jp) 키워드 알림 봇. 새 매물과 가격 인하를 찾아 텔레그램으로 알립니다.

## 구성

| 파일 | 역할 |
|---|---|
| `check_mercari.py` | 검색·판정(`--mode collect`)과 텔레그램 전송(`--mode send`) |
| `seen_items.json` | 봇의 상태. 이미 본 매물, 보낸 알림, 키워드별 조회 시각 |
| `merge_seen.py` | 실행이 겹쳐 push가 충돌했을 때 상태를 안전하게 병합 |
| `scripts/push_state.sh` | 상태 파일을 원격에 반영(충돌 시 병합 후 재시도) |
| `scripts/squash_history.sh` | git 이력 압축 (아래 "저장소 용량 관리" 참고) |
| `scripts/notify_failure.sh` | 워크플로 실패를 텔레그램으로 알림 |
| `.github/workflows/mercari-check.yml` | 알림 봇 본체 |
| `.github/workflows/squash-history.yml` | 저장소가 커지면 이력을 자동 압축 |

## 키워드 추가하기

`check_mercari.py`의 `SEARCHES`에 추가하면 됩니다. 새로 추가한 키워드는 **첫 조회에서
기준선만 저장하고 알림을 생략**하므로, 기존 매물이 한꺼번에 알림으로 쏟아지지 않습니다.
다음 조회부터 정상 동작합니다.

## 실행 주기 설정

`check_mercari.py`의 `FULL_SCAN_INTERVAL_SECONDS` 하나로 조절합니다.

| 값 | 동작 | 권장 상황 |
|---|---|---|
| `5 * 60` | 새 매물은 매 실행, 가격 인하는 5분마다 | 1분 주기로 돌릴 때 |
| `0` | 매 실행마다 전부 조회 | 2분 이상 주기로 돌릴 때 |

## 동작 점검

실행 로그에 매번 아래 줄이 남습니다.

```
[점검] 매물 2861개 확인 / 등록시각 있음 2861개 / 판매자ID 모름 387개
```

`등록시각 있음`이 **0이면 경고가 함께 출력**됩니다. 이 값은 "오래된 매물을 신규로
오인하지 않는" 방어선이 쓰는 값이라, 0이 되면 그 방어선이 상태 파일 기준으로만
동작하게 됩니다. 로그에서 이 줄을 확인하세요.

## 고장 감지

이 봇은 평소에 조용한 게 정상이라, 고장이 나도 "새 매물이 없나 보다"와 구분되지 않습니다.
그래서 두 가지 경로로 이상을 알립니다.

| 상황 | 알림 |
|---|---|
| 모든 키워드 검색이 10분 넘게 실패 | `⚠️ 메루카리 알림봇 이상` (이후 6시간마다 최대 1회) |
| 검색이 다시 성공 | `✅ 메루카리 알림봇 정상 복구` |
| 워크플로 실행 자체가 실패 | `⚠️ 메루카리 알림봇 실행 실패` + 실행 로그 링크 |

**알림 폭탄을 막는 장치가 핵심입니다.** 봇이 1분마다 돌기 때문에, 실패할 때마다 알리면
하루 1,400건이 넘습니다. 그래서:

- 검색 실패는 한 번으로 알리지 않고 **10분 이상 이어질 때만** 알립니다(일시적 오류 무시).
- 고장이 계속돼도 `alert_id`에 시간 구간이 들어가 **6시간당 한 번만** 나갑니다.
- 워크플로 실패는 **직전 실행이 성공이었을 때만** 알립니다(고장이 이어지는 동안은 조용).

검증: 24시간 전량 실패 시 알림 5건, 워크플로 60회 연속 실패 시 알림 1건.

감지할 수 없는 것: **봇이 아예 실행되지 않는 경우**(cron 서비스 중단 등)는 스스로 알 수
없습니다. 워크플로의 5분 스케줄이 백업 역할을 하지만, 완전한 감지는 외부 감시가 필요합니다.

## Actions 탭에서 "취소됨"이 보이는 이유

1분 주기로 돌리는데 한 실행이 50~90초 걸리기 때문에, 실행이 끝나기 전에 다음 트리거가
오면 대기하다가 그다음 트리거에 밀려 취소됩니다(실측 약 9%). **정상 동작입니다.**
`concurrency` 설정이 실행을 하나씩만 돌게 지켜 주는 결과이고, 실측 실행 간격은
평균 0.96분으로 유지됩니다.

## 저장소 용량 관리

상태 파일을 매 실행마다 커밋하므로 **git 이력**이 계속 쌓입니다.

- 커밋당 약 1.6KB (git 델타 압축이 잘 먹습니다)
- 1분 주기 기준 **1년에 약 1.2GB**
- 상태 파일 자체는 상한이 있어 **약 2MB에서 멈춥니다** (무한히 커지지 않음)

즉 정리 대상은 파일이 아니라 이력입니다. `squash-history.yml`이 **매주 저장소 크기를
확인해 임계치(기본 500MB)를 넘을 때만** 이력을 커밋 하나로 압축합니다. 평소에는
크기만 확인하고 아무것도 하지 않습니다.

**`seen_items.json`의 내용을 지우면 안 됩니다.** 이력이 줄지 않을뿐더러(오히려 커밋이
하나 더 늘어납니다), `sent_alerts`를 잃으면 이미 보낸 알림이 다시 나갈 수 있습니다.

압축이 안전한 이유:

1. `git commit-tree`로 **현재 트리를 그대로 가리키는** 부모 없는 커밋을 만듭니다.
   파일을 다시 쓰지 않고 트리 객체를 재사용하므로 상태가 달라질 여지가 없습니다.
2. `--force-with-lease`로 밀어냅니다. 읽은 시점 이후 봇이 상태를 갱신했다면 푸시가
   거부되어 아무것도 잃지 않고, 최신 상태로 다시 시도합니다.
3. 압축이 봇 실행 도중에 떨어져도, 봇은 `push_state.sh`의 병합 경로로 복구합니다.

수동으로 실행하려면 Actions 탭에서 `Squash State History`를 `workflow_dispatch`로
돌리면 됩니다. `dry_run=true`로 크기만 확인할 수도 있습니다.

## 액션 버전

`actions/checkout@v7`, `actions/setup-python@v7`을 씁니다. 둘 다 Node 24에서 네이티브로
동작해서 Node 20 지원 종료 경고가 뜨지 않습니다. 메이저 태그(`@v7`)를 쓰므로 그 안의
패치 업데이트는 자동으로 따라갑니다.

## 테스트

```bash
python -m unittest discover -s tests
```

봇 워크플로가 매 실행 전에 이 테스트를 돌리므로, 실패하면 그 실행은 알림을 보내지 않습니다.
